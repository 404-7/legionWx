# 联机同步原理与本轮优化

服务器每 50 毫秒推进战斗（20 次/秒），处理移动、攻击、经济、波次和胜负。玩家点击买兵、升级等按钮时，只提交指令；服务器验证身份、资源、阶段及规则后执行。浏览器负责绘图，不自行判定联机战斗结果。

服务器通过 SSE 长连接向浏览器推送状态，保持每秒 10 次的发送频率。HTTP POST 负责玩家操作，SSE 负责下行结果；没有改成客户端自行模拟，也没有降低战斗计算频率。

## 之前为什么费带宽

每次推送都重复发送完整状态，包含单位的大量寻路、攻击计时和仇恨内部字段；同一个单位的固定属性和未变化信息也会持续重复。兵种定义此前已用 ID 引用，但完整状态仍然很大。

## 当前处理流程

1. 按阵营过滤战争迷雾，敌方经济和不可见单位先从快照中剔除。
2. 只保留显示、选中和操作所需的单位字段。仇恨、目标锁定、攻击前摇等留在服务器；客户端需要的行为文字只保留 `brain.state`。传输数值保留两位小数，服务器内部计算精度不变。
3. 第一次发送完整基准，以后发送增量。单位按 `entityId` 匹配，独立处理新增、修改、删除和顺序变化，避免一个怪物死亡导致整个数组重发。玩家按 ID 匹配，国王按阵营匹配。
4. 每 100 个广播帧发送完整校准帧（正常约 10 秒）；新连接始终收到完整基准，不依赖先前连接的增量。
5. 每帧携带序号与基准序号。客户端发现序号不匹配会重新连接并取完整状态。客户端保留独立的协议基准，避免界面选中状态、兵种定义还原污染下一次增量。
6. 浏览器支持 gzip 时使用流式压缩，压缩等级 3，每帧 `Z_SYNC_FLUSH` 立即输出。支持无压缩回退；慢连接积压超过限制会断开并走重连。旧客户端仍可用完整状态协议。

同阵营快照、增量编码和文本帧在一次广播内复用，压缩器按连接独立维护。房间仍存于当前 Node 进程内存；这轮没有实现跨进程房间分配或服务重启后的对局恢复。

## 本地对比

运行 `node scripts/benchmark-sync.cjs`，同一批模拟状态同时进入旧完整状态协议与新增量压缩协议。每个场景模拟 12 秒，包含初始完整帧和周期校准帧，统计 SSE 文本和实际 gzip 输出；不包含 TCP/TLS 开销与资源下载。

## 部署注意

反向代理应允许 SSE 长连接，关闭 `/api/events` 的代理缓冲和缓存，并保留 `Content-Encoding` 与 `X-Accel-Buffering` 响应头。Node 已完成压缩，不要再对该响应重复压缩。TLS、代理空闲超时和客户端网络需在实际部署环境验证。

修改协议后刷新页面加载新的版本化脚本；仅重启 Node 无法替换用户已加载的客户端脚本。
